Your to-do list is the remote control for your AI agent.

Check a box, and the work comes back done. Two linked Notion databases — your ToDos and an Agent Hitlist — turn the list you already keep into a handoff queue: you flag a task, the agent picks it up, does it, and files the result right back under the task. No shortcuts, no voice commands, no new app.

Why Notion

Why not just a shortcut?

The pattern started as voice shortcuts for an Apple Watch and a HomePod. It works — but the Notion version is the one that stuck, because the list itself does the talking.

No new app to open

The handoff happens inside the to-do list you already maintain. There's nothing to launch, dictate, or learn — just a checkbox on a row you were writing anyway.

The work lives where you plan

The result is filed as a subpage under the task, next to your notes and context — not buried in a chat thread you have to search for later.

The task is the audit trail

Ask, status, and result sit on one page. You can see what was requested, when it was claimed, and exactly what came back — and verify it live.

Any device with Notion

Phone, laptop, tablet — flag a task from wherever you're planning, and pick up the finished result from wherever you are.

Under the hood

The plumbing, briefly

THE FORWARDER
A small watcher on a Linux box (Daisy) scans the ToDos for Ready for Cowork ✓ + Status “Not started” and hands each matching task to the agent in chat. When it forwards, it verifies both conditions first — so a task is never sent twice or sent half-ready.
POST & DEQUEUE
The relay underneath is a post-and-dequeue queue: a client POSTs a message, the agent works on it, and the client polls until the reply lands — consume-on-read, exactly-once delivery, 10-minute expiry. It was built for an Apple Watch and HomePod: a watch can't accept inbound connections, so the device pulls its reply when it's ready. Notion tasks ride the same idea — the list is just a calmer client.
STATE MACHINE
Every task moves Not started → Active → Done. Active is the claim — it stops double-work. Flipping a Done task back to Not started with Ready still checked starts a fresh round on the same page, so tasks iterate in place instead of piling up duplicates.
RESULT SUBPAGES
Results are written as a subpage under the task, never over it. Your wording, notes, and history stay intact; the agent's work is appended where you can find — and check — it.

Getting Started

Build it yourself, in eight steps

This is how the system above is actually put together — the real deployment, inspected November 13, 2026. Where a step depends on your own accounts (pairing the SDK, subscribing the webhook), it says what the step does and what it needs; the exact clicks are yours.

  1. 1

    Start with an always-on Linux box

    Any small machine that's always on and on your network will do. This deployment runs on Daisy, a Raspberry Pi 3 Model B Plus (aarch64, Debian 13) on the home network. It hosts one relay program that everything else hangs off of.

  2. 2

    Install the Muse gadget SDK and pair it

    The relay talks to the agent through the Muse gadget SDK — a command-line tool that, once installed and paired with your Muse account, can deliver a message into one of your chats. In this deployment it lives at /opt/musegadget/venv/bin/musegadget, and the relay delivers a task by running:

    musegadget send-user-msg --session-id <chat-uuid> <message>

    Installing the SDK and pairing it is what connects the Pi to your Muse chats — follow the SDK's own pairing flow with your account; there's nothing else to configure on the Notion side for this step.

  3. 3

    Put the relay on it

    The relay is a single Python 3 file — server.py — using only the standard library (http.server), so there are no pip dependencies to install. It listens on 0.0.0.0:8098 and is started with:

    python3 server.py

    Leave it running. In this deployment it has run continuously since October 18, 2026, logging to server.out and push.log. Its jobs: receive the Notion webhook, check the Ready gate (step 7), and — only when the gate passes — hand the task to the agent via the SDK.

  4. 4

    Expose it with a Cloudflare Tunnel

    Notion's webhook needs a public HTTPS address, but you don't need to open ports on your router. cloudflared runs on the Pi and exposes the relay through a Cloudflare Tunnel — here, as daisy-push.delianpetrov.com. The tunnel authenticates from a token file at /etc/cloudflared/token. No port forwarding on the home router.

  5. 5

    Set up the two Notion databases

    You need two databases, linked by a relation:

    • ToDos — yours, the list you already keep.
    • Agent Hitlist — the agent's queue, linked to ToDos.

    Each Hitlist row carries a Title, a “Ready for Cowork” checkbox, and a Status that moves Not started → Active → Done. The agent also needs Notion API access that can read pages and blocks, create subpages, and update the Status — in this deployment, a personal Notion integration used from the command line.

  6. 6

    Subscribe the webhook — and verify it

    Create a Notion webhook subscription on the Agent Hitlist database that sends events to:

    POST https://daisy-push.delianpetrov.com/notion

    (Your URL will be your own tunnel hostname.) During setup, Notion sends a verification_token; the server saves it to a file with 0600 permissions and then uses it to HMAC-SHA256-verify every incoming event via the X-Notion-Signature header — a bad signature gets a 401 and is dropped. The server only accepts page.created, page.content_updated, and page.properties_updated events, and dedupes by event id (the last 500 are kept).

  7. 7

    Add the Ready gate — the safety piece

    A webhook fires for every change, including the agent's own writes. So before forwarding anything, the server asks a small Cloudflare Worker for the current Ready list — exactly the Agent Hitlist rows with “Ready for Cowork” checked AND Status “Not started.” The worker endpoint is token-authenticated, with the token kept in a 0600 file on the Pi.

    Anything not on that list — ToDo rows, other databases, subpages, and the echoes of the agent's own claim and completion writes — is dropped on the Pi and never reaches the chat. Each page is forwarded at most once per 30 minutes, and if the gate is unreachable the server fails closed: drop and log, never forward.

    When the gate passes, the forwarded message tells the agent the page id, that the gate was verified, and the workflow: fetch the page, claim it (Status → Active), do what it asks, write the result as a subpage — never replacing the task's content — then mark Status → Done.

  8. 8

    Try it

    Write one small task in your ToDos, check its Ready for Cowork box, and watch: it appears on the Hitlist, flips to Active while the agent works, and comes back Done with the result filed as a subpage underneath it. That's the whole loop from the top of this page, running on your own list.

Same server, second job. The relay also runs the dequeue side of the original voice route: a client POSTs a reply to /enqueue (authenticated by an X-Push-Secret header matching a 0600 secret file), the reply is appended to a JSON queue file — a fresh reply clears stale ones, and follow-up chunks of one reply use append=true — and polling clients like the Apple Watch and HomePod shortcuts GET the queue until their reply lands. You only need this half if you want the voice route too.

Optional backstop, currently off. The setup also has a 5-minute poller that re-checks the Ready list in case a webhook is ever missed. It exists but is not running — the webhook plus the gate has been enough.
